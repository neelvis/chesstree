# ChessTree — продуктовая спецификация шахматных ботов

Версия: 1.0 · Дата: 29 сентября 2026 · Статус: спецификация для планирования и технической декомпозиции.

Основание: исследование алгоритмов для шахмат на троих и обсуждение в этом чате. Репозиторий ChessTree, точные правила и производительность устройств ещё не исследованы. Численные требования ниже — предлагаемые критерии разработки, а не достигнутые результаты. Сроки и рекомендации по моделям — инженерная оценка.

## 1. Продуктовое решение

Создать быстрых компьютерных соперников для ChessTree на общем игровом движке. Игрок выбирает характер и уровень сложности независимо. Бот соблюдает правила ChessTree, учитывает интересы двух соперников, отвечает в ограниченное время и не блокирует интерфейс.

Первая версия: четыре характера, три уровня сложности, локальная тренировочная партия, воспроизводимые партии ботов и измерение качества. Бот выбирает ходы алгоритмически, без обращения к языковой модели во время игры. Языковые модели используются при разработке и анализе результатов.

Рекомендуемый путь: существующее ядро правил → контрольный Maxⁿ → кандидат Paranoid с alpha-beta → сравнение при одинаковом времени → профили поведения. Paranoid остаётся кандидатом, а не заранее объявленным победителем. Если он проигрывает Maxⁿ по критериям ниже, выпускается лучший подтверждённый вариант.

## 2. Пользователи, задачи и границы

| Пользователь | Задача | Ожидаемый результат |
|---|---|---|
| Новичок | Научиться играть без ожидания соперников | Понятный выбор сложности, доступная партия, отсутствие зависаний |
| Регулярный игрок | Тренироваться против разных манер | Атакующий и позиционный соперники заметно различаются |
| Опытный игрок | Проверить тактику и позднюю стадию | Бот учитывает третью сторону и уверенно завершает простые выигрышные позиции |
| Разработчик | Воспроизвести ошибку или сравнить версии | Сохранены позиция, версия правил, настройки и диагностические данные |

**Входит в v1:** один подтверждённый набор правил ChessTree; человек против двух независимых ботов; выбор профиля и сложности для каждого; сохранение и продолжение партии; отмена вычисления; четыре характера; три уровня; стенд турниров; локальная диагностика; интеграция Android/iOS/Web при подтверждении существующей KMP-архитектуры на E0.

**За пределами v1:** обучение нейросети, полноценный MCTS, динамические коалиционные модели, большая база эндшпилей, перенос всего Stockfish, рейтинг в единицах обычного шахматного Elo, объяснения ходов через LLM, автоматическая подстройка сложности без ведома игрока.

Серверное выполнение для онлайн-партий — следующий этап, если его не требует уже существующая архитектура. Интерфейс движка должен позволять такой перенос. Если сервер необходим уже для тренировочных партий, E0 пересчитывает объём и сроки. Нельзя незаметно добавлять обязательный новый backend в текущую оценку.

## 3. Решения по правилам до реализации поиска

На E0 извлечь правила из существующего кода и подтвердить спорные случаи у владельца продукта. Готовые правила повторно не изобретать. Пока не определены победа и допустимость ходов, допускается работа над интерфейсами и стендом, но нельзя принимать стратегию поиска.

| ID | Решение | Почему необходимо |
|---|---|---|
| R01 | Первый мат завершает партию или игрок выбывает? | Определяет терминальные состояния и цель поиска |
| R02 | Победитель один? Как оцениваются второе место и ничья? | Определяет вектор награды |
| R03 | Когда фиксируется мат и кто считается его автором? | Между атакой и ответом может ходить третья сторона |
| R04 | Разрешён ли ход под шах; нужно ли немедленно защищать короля? | Определяет легальность и тактический поиск |
| R05 | Что происходит с фигурами и ходами выбывшего? | Меняет геометрию занятости и очередь |
| R06 | Как определяются пат, повторения и отсутствие прогресса? | Поиск должен корректно завершать циклические линии |
| R07 | Геометрия, лучи через центр, направления пешек, превращения | Определяет генератор ходов и оценку |
| R08 | Особые фигуры и их правила движения | Визуальные образы не считаются новыми типами без подтверждения |
| R09 | Рокировка, взятие на проходе, сдача, истечение времени | Все существенные права и переходы входят в состояние |

Результат: версионированный контракт правил и примеры позиций с ожидаемыми исходами. Терминальная награда определяется правилами отдельно от эвристической оценки. При единственном победителе допустима награда (1,0,0); при других правилах она изменяется явно. Нельзя самостоятельно награждать второе место, если продукт этого не предусматривает.

## 4. Пользовательские сценарии и требования

| ID | Требование | Приёмочный сценарий |
|---|---|---|
| F01 | Для каждого бота доступны характер и сложность | Игрок создаёт партию с атакующим новичком и сильным позиционным ботом |
| F02 | Настройки сохраняются с партией | После перезапуска возвращаются те же профили, сложность и версия правил |
| F03 | Бот делает только допустимые ходы | Любой предложенный ход валидируется игровым ядром перед применением |
| F04 | Видно, кто думает | Во время поиска показан индикатор; меню, камера и навигация остаются отзывчивыми |
| F05 | Уход из партии отменяет поиск | Результат старой задачи не меняет другую или уже закрытую партию |
| F06 | Позиция защищена от устаревшего результата | После отмены хода или загрузки состояния принимается только ответ с текущей версией позиции |
| F07 | Ограничение времени не оставляет игру без хода | При исчерпании бюджета возвращается лучший завершённый результат или заранее проверенный допустимый ход |
| F08 | Конец партии обрабатывается отдельно | При отсутствии допустимых ходов возвращается исход по правилам, а не случайный ход |
| F09 | Боты независимы | Нет общего плана двух ботов против человека; решения используют публичную позицию и собственную цель |
| F10 | Сложность не меняется скрыто | Выбранный уровень постоянен в партии; изменение через UI относится к новой партии |
| F11 | Сбой не приводит к бесконечному ожиданию | Контроллер завершает запрос; валидный резервный ход допустим только для текущей позиции; иначе показывает возможность повторить |
| F12 | Диагностика воспроизводима | Экспорт содержит начальное состояние, ходы и версии без лишних пользовательских данных |

Искусственная пауза для анимации, если понадобится, не входит во время вычислений и не маскирует медленный поиск. Обычный пользователь не видит технические термины Maxⁿ, alpha-beta и таблица транспозиций.

## 5. Характеры и уровни

| Профиль | Обещание игроку | Реализация | Ограничение |
|---|---|---|---|
| Универсальный | Играет сбалансированно | Базовые веса и адаптация к фазе | Не менять цель партии ради стилистического эффекта |
| Атакующий | Ищет инициативу и давление | Активность, устойчивые угрозы, давление на короля | Не награждать любой шах или бессмысленную жертву |
| Позиционный | Укрепляет позицию и готовит действия | Безопасность, структура, мобильность, ограничение второго фронта | Не поощрять бесконечное ожидание |
| Эндшпилист | Силен в превращениях и маломатериальной игре | Отдельные признаки поздней стадии, пешечные гонки, оценка перехода в дуэль | Не считать любой размен выгодным |

Все профили используют общую модель правил и инфраструктуру поиска. Сначала стиль выбирает среди близких по общей оценке ходов. Порог близости настраивается экспериментально; найденная терминальная победа важнее стиля, а доказанная в рамках модели поиска потеря не выбирается при наличии лучшего результата. Ограниченный поиск не является доказательством объективной безопасности.

Если фильтра близких ходов недостаточно для узнаваемости, разрешается профильная оценка листьев. Такие результаты разделяются в кеше по версии оценки и профилю. Небольшая случайность допустима при близких альтернативах, с сохраняемым seed. Случайные грубые ошибки не являются основным способом снижения силы.

| Уровень | Мягкий бюджет | Порог остановки поиска | Поведение |
|---|---:|---:|---|
| Начальный | 100 мс | 150 мс | Небольшой бюджет, ограниченная вариативность среди разумных ходов |
| Обычный | 350 мс | 500 мс | Основной продуктовый режим |
| Сильный | 900 мс | 1200 мс | Больше поиска и более строгий выбор |

Это начальные настройки. Они фиксируются перед итоговым сравнением, а не подгоняются по закрытому тестовому набору. Характер и сложность выбираются независимо; сила между уровнями подтверждается турнирами. Нельзя обещать одинаковую силу на телефонах с разной производительностью при одинаковом времени.

## 6. Архитектурные ограничения

| Компонент | Ответственность |
|---|---|
| RulesCore | Авторитетные правила, легальность, завершение и повторения |
| SearchPosition | Компактная позиция, make/unmake, хеш состояния |
| Evaluator | Вектор оценок для A/B/C, фаза и терминальные исходы |
| SearchEngine | Контрольный Maxⁿ и Paranoid с явными MAX/MIN |
| BotProfile | Стиль, параметры оценки и выбора хода |
| BotRunner | Выполнение вне UI, таймер, отмена, ограничение ресурсов |
| Arena | Партии, турниры, сбор метрик и сравнение версий |

Интерфейс запроса содержит requestId, rulesVersion, engineVersion, positionVersion, полную позицию и необходимый контекст повторений, playerId, profile, difficulty, seed, timeBudget и необязательный nodeBudget. Ответ содержит тот же requestId/positionVersion, ход либо терминальный статус, причину остановки, elapsedMs, nodes, completedDepth и версию оценки. Нельзя выдавать эвристическое число за калиброванную вероятность победы.

Базовый технологический выбор — использовать существующее общее ядро ChessTree. На E0 установить фактический стек; если это KMP, начать с общего Kotlin-кода. Rust/C++ рассматривается только при доказанном узком месте и сравнительном прототипе. Не вести две независимые реализации правил без дифференциальной проверки.

Геометрия кодируется индексами клеток и предрассчитанными траекториями. Лучи учитывают переходы через центр по реальным правилам. Начать с массивов и списков фигур; битовые маски вводить по профилю производительности.

Переиспользовать из обычных движков архитектурные идеи: make/unmake, сортировку ходов, углубление, хеширование, инкрементальную оценку. Генератор, двухсторонний negamax, готовые веса NNUE и стандартные эндшпильные базы не переносить как готовое решение. Заимствованный код должен иметь зафиксированное происхождение и подходящие условия лицензии.

## 7. Поиск, оценка и эндшпиль

**Maxⁿ:** в каждом узле текущий игрок выбирает продолжение с лучшей собственной компонентой; вверх возвращается весь вектор. Равенства разрешаются стабильным правилом. Контрольный режим с фиксированным числом узлов детерминирован.

**Paranoid:** корневой игрок максимизирует свою оценку; оба соперника минимизируют её. При очереди A/B/C используется MAX/MIN/MIN, без автоматической смены знака на каждом полуходе. Модель может переоценивать враждебную координацию; это проверяется отдельно на позициях с конфликтом интересов соперников.

**Оценка:** материал, активность, безопасность короля от двух армий, пешечная структура, превращения, фактический порядок ходов, последствия разменов для третьего игрока, цена второго фронта, переход к двум участникам. Для правил «первый мат побеждает» требуется учитывать угрозу победы соперника над третьей стороной.

**Поздняя стадия:** определять по активному материалу и угрозам, а не номеру хода. При двух активных участниках двухсторонний поиск допустим лишь при соответствующей структуре наград и правил; доска остаётся доской ChessTree. Эндшпилист не получает скрыто больше времени, чем другие характеры того же уровня.

**Тактическое продолжение:** ограниченная дополнительная глубина для нестабильных позиций. Нельзя останавливаться статической оценкой в обязательном ответе на шах, пропускать промежуточный ход третьего игрока или расширять дерево без общего дедлайна.

**Кеш:** учитывать полный существенный статус позиции, сторону хода, права, активных игроков и контекст повторений; отделять модель поиска, корневого игрока для Paranoid, профиль и версию оценки. Если историю нельзя безопасно включить в ключ, ограничить применимость записей в зависимых от неё позициях. Незавершённую ветвь не сохранять как точный результат.

Не включать в первую принятую версию null-move pruning, сложные сокращения глубины и гибридное переключение моделей. Каждая такая оптимизация — отдельная гипотеза с измерением качества и скорости.

## 8. Скорость, ресурсы и устойчивость

На E0 выбрать конкретные эталонные Android, iPhone и браузерное устройство; зафиксировать модель, ОС, сборку и режим питания. Производительность измерять в release-сборке, с холодными и прогретыми запусками, а также в серии ходов для выявления перегрева. Для браузера поиск выполняется в worker. Время запроса включает получение резервного хода и сериализацию; отдельно измеряются очередь, вычисление и применение результата.

| ID | Предлагаемый критерий выпуска |
|---|---|
| N01 | На каждом согласованном эталоне p99 вычисления ≤ порог остановки + max(20 мс, 10% порога) на минимум 1000 репрезентативных запросов |
| N02 | Порог соблюдается и в тактическом продолжении, и при генерации большого числа ходов; любой перелёт более 2× порога расследован |
| N03 | От запроса отмены до завершения вычисления p95 ≤ 50 мс и p99 ≤ 100 мс на эталонах |
| N04 | Нет синхронного поиска на UI-потоке; ухудшение доли медленных кадров в стандартном сценарии ≤ 2 процентных пунктов относительно сцены без поиска |
| N05 | Начальный лимит таблицы транспозиций — 16 MiB; целевой прирост пиковой памяти движка ≤ 64 MiB относительно приложения без него |
| N06 | Только один активный поиск на партию; повторный запрос отменяет предыдущий; число одновременно работающих поисков ограничено |
| N07 | 0 применённых устаревших результатов в сценариях отмены, восстановления, окончания и повторной загрузки партии |

Это эксплуатационные SLO, а не обещание жёсткого реального времени: планировщик ОС может приостановить процесс. Фоновый переход отменяет поиск или сохраняет состояние по правилам платформы; возобновление создаёт новый запрос. Бюджет памяти и эталоны подтверждаются на E0/E1, изменение порогов оформляется решением, а не скрытой правкой теста.

При первом входе в поиск заранее сохраняется допустимый ход. При таймауте выбирается последний полностью завершённый результат. Если позиция терминальна, корректен терминальный ответ. Резервный ход — восстановление после ограничения ресурсов, а не оправдание систематических таймаутов.

## 9. Проверка качества и критерии приёмки

### 9.1. Корректность

- Набор правил: не менее 60 вручную разобранных позиций, покрывающих R01–R09; ожидаемые исходы подтверждены независимо от реализации поиска.
- make/unmake восстанавливает все поля и хеш; дополнительно сравнивается полная сериализация, чтобы ошибка хеша не скрывала повреждение.
- Если быстрый генератор отличается от игрового, выполнить дифференциальную проверку минимум 10 000 достижимых состояний. Если генератор один, использовать независимые эталонные примеры и инварианты.
- За проверочные турниры — ноль недопустимых ходов, ошибок терминального исхода и порчи состояния. Большое число партий не заменяет разбор граничных случаев.

### 9.2. Тактика и сила

- Собрать минимум 200 тактических и стратегических позиций; 120 открытых для разработки и 80 закрытых для итоговой оценки. Разделять по происхождению сценариев, а не случайно разрезать почти одинаковые позиции.
- Для стратегических позиций задавать множество допустимых хороших решений или оценку поведения; не требовать единственного субъективного хода.
- Обязательные простые терминальные победы и обязательная защита в выделенном поднаборе: 100% у обычного и сильного уровней. Общая цель на закрытом наборе для обычного — ≥ 85%, для сильного — не ниже обычного. Порог уточняется один раз после калибровки сложности на E2, до открытия holdout.
- Сравнивать Paranoid и Maxⁿ при одинаковом времени на одном оборудовании против фиксированного набора соперников: жадного, контрольного и предыдущей принятой версии.
- Перед выпуском провести предварительно зафиксированный турнир минимум 600 партий на сравниваемую конфигурацию с балансом мест, стартов и seed. Окончательный размер оценить по разбросу пилота; при неопределённом результате нельзя объявлять улучшение.
- Все шесть назначений трёх разных агентов по местам представлены одинаково. Повторные партии одного старта считать зависимым блоком; доверительные интервалы вычислять с учётом блоков.
- Основная метрика — награда по утверждённым правилам; отдельно победы, ничьи, выбывание, длительность и ошибки. Не предполагать, что случайный ориентир всегда ровно 33%.
- Для принятия основного движка: нижняя граница 95% интервала разницы средней нормированной награды относительно Maxⁿ не ниже −0,03, тактические и временные критерии пройдены. Это допуск неухудшения, а не доказательство превосходства. При провале остаётся Maxⁿ или предыдущая принятая версия.
- Для уровней сложности ожидается положительное различие более сильного уровня в фиксированном пуле; если интервал разницы включает ноль, обещание различимой силы ещё не подтверждено.

### 9.3. Узнаваемость профилей

- На отдельном наборе спокойных позиций с близкими альтернативами атакующий чаще выбирает активные угрозы, позиционный — улучшение безопасности/структуры. Порог на пилоте: профильный выбор отличается от универсального минимум в 20% подходящих позиций.
- Эндшпилист проходит отдельный набор пешечных гонок и переходов в дуэль; преимущество проверяется при том же времени. Название «эндшпилист» не считается выполненным одним увеличением веса пешек.
- Допустимое снижение средней нормированной награды профиля относительно универсального — до 0,05 при отсутствии регресса в обязательной тактике; неопределённость публикуется рядом с результатом.
- Пользовательская проверка: ориентир 8–12 участников, по две короткие сессии. Проверить понятность выбора, восприятие ожидания и способность описать различия без подсказки. Это качественная проверка, не статистическое доказательство силы.
- Отдельно разбирать партии человека против двух ботов: временное совпадение интересов разрешено, специальная враждебность к человеку не допускается. Код решения не использует признак «человек» для оценки цели атаки.

## 10. Этапы, время проверки и осмысления

Базовый план: один разработчик, существующий работающий движок правил и приложение. Один рабочий день — планировочная единица, не длительность ответа модели. Ускорение генерации кода не убирает время эксперимента и продуктовой проверки.

| Этап | Реализация, дней | Проверка и разбор, дней | Результат и условие перехода |
|---|---:|---:|---|
| E0. Правила и границы | 2 | 1 | Контракт R01–R09, аудит стека, эталоны, список допущений; существенных неопределённостей нет |
| E1. Поисковое состояние | 5 | 2 | Генерация, make/unmake, хеш; пройдена корректность и измерена стоимость узла |
| E2. Контрольный бот | 3 | 1 | Maxⁿ, базовая оценка, Arena, калибровка позиций; нет ошибок очереди и исходов |
| E3. Быстрый кандидат | 6 | 2 | Paranoid, дедлайн, сортировка, кеш; сравнительный отчёт и решение о базовом алгоритме |
| E4. Характеры и эндшпиль | 4 | 2 | Четыре профиля; измерены различия, сняты грубые тактические регрессии |
| E5. Интеграция и опыт игры | 5 | 2 | UI, сохранение, отмена, три платформы при подтверждённом стеке; продуктовые сессии и профилирование |
| E6. Стабилизация и выпуск | 3 | 1 | Закрытый набор, фиксированный турнир, финальное ревью, версия для выпуска |
| Итого | 28 | 11 | 39 рабочих дней до резерва |

Дополнительно 6 рабочих дней резерва на обнаруженные дефекты и повторную проверку исправлений. Базовый срок — 45 рабочих дней, около 9 рабочих недель. Диапазон планирования — 8–12 недель; после E1 выполнить переоценку. Отсутствие общего ядра, необходимость нового backend или переработка правил требуют отдельной оценки. Набор участников для проверки может удлинить календарный срок без увеличения трудозатрат.

Пример ритма: недели 1–2 — E0/E1; неделя 3 — E2 и начало E3; недели 4–5 — E3/E4; недели 6–7 — E5; неделя 8 — E6; неделя 9 — резерв. Это относительный план без обещания даты начала.

### Обязательный цикл на каждом этапе

1. Зафиксировать гипотезу и критерий до написания изменения.
2. Получить минимальную законченную реализацию и сохранить воспроизводимую версию.
3. Выполнить только релевантные проверки и сравнить с предыдущей принятой версией.
4. Разобрать минимум 10 содержательных случаев: ошибки, неожиданное поведение, улучшения и ухудшения. Для инфраструктуры это трассы и инварианты, для стратегии — позиции и партии.
5. Выделить 1–2 часа на письменный разбор; на E1/E3/E4/E5 оставить повторное чтение выводов на следующий рабочий день. Это смена контекста и анализ данных, а не дополнительный бесцельный вызов модели.
6. Записать решение: принять; вернуть на исправление; откатить; провести один ограниченный эксперимент. Указать факты, неопределённость и влияние на срок.

Дни проверки включают выполнение тестов/турниров, человеческий разбор и небольшие исправления. Крупные переделки берутся из резерва и отражаются в плане. Техническое решение о переходе принимает ответственный разработчик по критериям; отдельное подтверждение владельца нужно при изменении правил, продуктового объёма или пользовательского обещания. Не превращать каждый технический шаг в запрос разрешения.

## 11. Рекомендации по моделям для разработки

Рекомендации относятся к помощникам разработчика. Бот в партии не использует GPT. Проверены официальные страницы OpenAI 29.09.2026 [S5–S7]: Sol позиционируется для повседневной разработки, Astra — для наиболее сложных задач, Luna — для ограниченных и экономичных задач. Привязка к этапам ниже — наша рабочая схема, которую следует проверить на задачах репозитория.

Доступность конкретных версий, настройки reasoning и расход лимитов зависят от продукта и аккаунта. Это не обещание наличия всех моделей в твоём интерфейсе. Не фиксировать неизвестные цены или множители credits. При недоступности выбранной модели явно обозначить замену, особенно если репозиторий требует конкретную модель.

| Этап / задача | Основная модель | Reasoning | Проверка результата |
|---|---|---|---|
| E0: формализация правил, спорная семантика победы | GPT-6 Astra | High | Разработчик подтверждает примеры; Sol проверяет согласованность интерфейсов |
| E1: архитектура состояния и инварианты | GPT-6 Sol | High | Astra High — один отдельный разбор рискованных переходов и отмены |
| E1–E3: генератор, Maxⁿ, Paranoid, кеш | GPT-6 Sol | High для алгоритмов; Medium для обвязки | Исполняемые тесты; Astra High на границе E3, если есть спорные отсечения или результаты |
| E2: подготовка фикстур по уже заданным правилам | GPT-6 Luna | Medium | Sol проверяет ожидаемые исходы; Luna не является единственным арбитром правил |
| E3: поиск причины нестабильности или регрессии | GPT-6 Astra | High; Extra high для узкого нерешённого случая | Минимальный воспроизводимый пример и эксперимент, а не только текстовое заключение |
| E4: оценка, стили, эндшпиль | GPT-6 Sol | High | Astra High — анализ неожиданных стратегических эффектов по выборке партий |
| E5: UI, сохранение, интеграция, отмена | GPT-6 Sol | Medium; High для конкурентности | Профилирование и сценарии жизненного цикла на устройствах |
| E6: итоговый аудит правил/поиска/рисков | GPT-6 Astra | High | Независимая сессия ревью с исходными требованиями и доказательствами |
| Документация, отчёты из готовых метрик, небольшие исправления | GPT-6 Luna | Low или Medium | Автоматическая валидация и выборочное ревью Sol |

Независимое ревью означает отдельный контекст с требованиями, diff, тестами и метриками, а не повторение авторского объяснения. Смена модели может помочь найти другие ошибки, но не гарантирует независимость или правильность. Для этой схемы не требуется постоянная параллельная работа нескольких агентов.

### Экономия лимитов без снижения приёмочного качества

- По умолчанию использовать Sol Medium; High включать на алгоритмах и конкурентности.
- Astra запускать на 3–4 ключевых рубежах и для конкретного нерешённого риска, а не после каждого коммита.
- Luna поручать ограниченную задачу с примерами, допустимыми файлами и критериями завершения. Не перекладывать на неё единоличное доказательство корректности поиска.
- Сначала выполнить пилот из 6 реальных задач: правила, make/unmake, исправление поиска, тест, UI, анализ отчёта. Сравнить принятый результат, число исправлений, время и фактический расход.
- Если две попытки решения не дали проверяемого прогресса, остановить повторение: уменьшить задачу, подготовить воспроизводимый случай и лишь затем повысить модель или reasoning.
- Не просить модель читать весь репозиторий в каждой задаче. Передавать карту модулей, контракт правил, минимальный контекст и ссылки на нужные файлы.
- При исчерпании лимита сохранить checkpoint с результатом и незавершённым риском. Не снижать критерии приёмки и не менять модель скрыто.

Карточка задачи для модели: цель; действующая версия правил; разрешённый объём изменения; входные примеры; критерий готовности; команды проверки; бюджет эксперимента; формат отчёта. Отчёт должен содержать проверенные факты и открытые вопросы, а не объявление «готово» без доказательств.

## 13. Риски и решения

| Риск | Как обнаружить | Действие |
|---|---|---|
| Неполные правила | Разные ожидания на одной позиции | Завершить контракт до приёмки поиска |
| Paranoid чрезмерно оборонителен | Проигрывает Maxⁿ, игнорирует конфликт интересов | Оставить Maxⁿ; гибрид исследовать отдельно |
| Быстрый генератор расходится с приложением | Дифференциальные расхождения | Исправить до оптимизации; не скрывать фильтрацией на выходе |
| Стили ухудшают игру | Регресс обязательной тактики или награды | Уменьшить силу стилевого выбора, сохранить профиль как предпочтение |
| Переобучение на тестовые позиции | Рост открытого набора без роста закрытого | Держать holdout закрытым, после утечки сформировать новый |
| Поиск тормозит UI | Трассы потоков и медленные кадры | Вынести исполнение, проверить сериализацию и применение |
| Модель уверенно предлагает неверный алгоритм | Контрпример, несовпадение с эталоном | Требовать исполняемое доказательство/тест и отдельное ревью |
| Оптимизация ускоряет, но ослабляет | Турнир при том же времени | Откатить либо оставить экспериментальной |
| Правки занимают больше резерва | Повторный провал рубежа | Пересчитать план; сократить второстепенный объём, сохранив корректность |

## 14. Условия выпуска и дальнейшие решения

Выпуск допускается, когда закрыты R01–R09, пройдены F01–F12 и N01–N07 на согласованных платформах, нет критических ошибок правил, опубликован сравнительный отчёт, сохранена предыдущая стабильная конфигурация для отката и назначен ответственный за исправления.

Порядок возможного сокращения объёма при задержке: сначала отложить продвинутые оптимизации и дополнительную случайность, затем согласовать выпуск меньшего числа характеров. Корректность, отмена, отзывчивость и защита от устаревшего результата не сокращаются. Меньшее число профилей — изменение продуктового объёма, требующее явного решения владельца.

После v1: MCTS сравнивать с принятой версией при тех же ресурсах; маленькую обучаемую оценку вводить лишь при наличии данных; серверный режим проверять под нагрузкой отдельно. Новый алгоритм не принимается только потому, что он сложнее или использует нейросеть.

Ближайший шаг разработки: E0 — открыть репозиторий, найти авторитетное ядро правил, заполнить R01–R09, зафиксировать устройства и подтвердить объём платформ. Эта спецификация не означает, что реализация или измерения уже выполнены.
